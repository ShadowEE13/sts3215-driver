最後一定要補（投影片上的紅字已拿掉）：

> 「這份介面已經凍結交給 B。後端第一版用 LeRobot，之後換成我的 C 驅動，B 完全不用改。」

### 名詞

- **UDP**：明信片，不保證送到、不保證順序，但不會因為一包掉了就卡住後面。TCP 像掛號信，保證送到但掉了要等重寄。每 10 ms 一個新位置，掉了就算，再用 `seq` 丟掉亂序到的舊包。
- **localhost**：同一台電腦自己傳給自己（127.0.0.1），B 的橋接和控制層跑在同一台 PC。
- **payload**：封包裡真正要傳的內容。`[標頭 20 B][payload][CRC 2 B]`。JOINT 的 payload 是 6 個 int32 共 24 bytes；NOP 心跳是 0 bytes。
- **CRC-16**：附在最後的 2 bytes 檢查碼，跟 STS3215 封包的 checksum 同概念，但抓錯能力更強。

### CRC-16：為什麼選、怎麼運作

**為什麼要有**（interface-spec-rationale §2.3）
1. 抓兩端**封包長度／位置**不一致：B 的結構多一個 padding、少一次對齊，或算 CRC 的範圍不同，CRC 立刻對不上
2. 作業系統在回送介面上可能略過 UDP 自己的 checksum 驗證
3. 以後改無線，欄位不用動

**⚠️ 不要說錯**：CRC **抓不到**欄位內容的位元組序寫反。B 把某欄位寫反，但 CRC 是對他實際送出的 bytes 算的，接收端重算一樣對得上。欄位內容靠 `magic` 比對和 v1.2 的 NOP 範例封包驗證（C-22）。

**為什麼是 16 位元**
- 比簡單加總強：加總不管順序

  | 內容 | 加總取反 | CRC-16 |
  |---|---|---|
  | `10 27 00 00` | `C8` | `9C31` |
  | `27 10 00 00`（前兩個對調） | `C8`（抓不到） | `A1C0`（抓到） |

- 封包最長 46 bytes，CRC-16 保證抓到所有 1～3 位元錯誤、所有奇數個位元錯誤、16 位元以內的連續錯誤；CRC-32 多 2 bytes 沒有實質好處
- CCITT-FALSE 常見，各語言都有實作，B 可以自己對照

**原理**：把資料當成很長的二進位數，除以固定的多項式 `0x1021`（x¹⁶ + x¹² + x⁵ + 1），16 位元餘數就是 CRC。減法換成 XOR，不進位，所以便宜。參考程式每處理一個位元，就是長除法「往下拉一位、夠除就減掉除數」那一步。初始值 `0xFFFF`。

**標準檢查值**：`"123456789"` → `0x29B1`（已用規格的演算法驗算）。變體差一點兩端都「看起來能跑」卻互相不認，所以先對這個值。

**一句話版本**
> 「CRC 是附在封包最後的檢查碼，把資料當成多項式除以固定除數取餘數。在 localhost 上主要用途是整合時抓兩端封包長度或格式不一致；封包最長才 46 bytes，CRC-16 就夠了。」

## P6　上層封包格式（約 40 秒）

**核心訊息**：用圖講封包長什麼樣，挑兩個紅色格子講，分別接前後頁。

> 「第二排是指令類型。紅色的 JOINT 是本學期主要用的，傳 6 個關節角度；紫色的 POSE 格式已經定好，下學期有 IK 才實作。另外有 ESTOP、RESUME 做急停，NOP 是心跳。」

- timestamp 那句承上啟下：「它就是 t0」接回 P4，「改過兩次」引出 P7
- 底下紅字不用念

### 欄位（被問才講）

| 欄位 | 大小 | 用途 |
|---|---|---|
| magic | 2 B | 固定 `0x5343`，確認是我們的封包 |
| version | 1 B | 協定版本，目前 `0x01` |
| cmd | 1 B | 指令類型 |
| seq | 4 B | 遞增序號，丟掉亂序的舊包 |
| timestamp | 8 B | 發送端時間戳，微秒 |
| payload_len | 1 B | payload 長度，接收端靠它找到 CRC 位置 |
| reserved | 3 B | 填 0，保留擴充；湊滿 20 bytes |
| payload | 0–24 B | 真正的內容 |
| CRC-16 | 2 B | 檢查碼 |

### seq 怎麼運作（§6.2、§6.3）

- B 每送一包 seq 加 1；控制層記住接受過的最大值
- 新包比記錄大 → 接受；小於或等於 → `STALE`，丟掉不重排，也不重置 watchdog
- 例：收到 101 → 103 → 102 → 104，102 被丟掉（晚到的舊位置照執行，手臂會往回抽）
- **重啟陷阱 F-28**：B 重開後 seq 從 1 算，全被當過期，手臂一直鎖住。C-21：watchdog 逾時就清除記錄，最多 200 ms 恢復，B 不用改
- 4 bytes：100 Hz 下約 497 天才溢位

### 各指令類型

- **JOINT（0x01）**：6 個 int32，單位 0.001 度，直接對應關節
- **POSE（0x02）**：x, y, z（0.01 mm）+ rx, ry, rz（0.001°，ZYX 尤拉角），夾爪在空間中的位置與姿態。要先用 IK 換算成關節角度。本學期沒有 IK、B 的座標系也還沒定（open-questions 01），所以回 `NOT_IMPLEMENTED`；欄位先凍結，B 可以先照格式開發
- **GRIPPER（0x03）**：一個 int32 `opening`，0 全閉、10000 全開。夾爪幾何由控制層換算，B 只要把手指彎曲程度換成 0～10000；換夾爪只改控制層
- **ESTOP（0x10）**：立即停止、保持位置（不斷電），之後 JOINT／POSE／GRIPPER 一律拒絕並回 `ESTOP_ACTIVE`，直到 RESUME。期間仍接受 NOP，watchdog 照常
- **RESUME（0x11）**：解除急停
- **NOP（0x00）**：空封包，重置 watchdog 但不改變目標。B 沒新資料時要持續送，否則 200 ms 後進入保持狀態
  - 收到 NOP = 連線正常、沒新目標；watchdog 逾時 = 可能斷線或 B 掛了，會清除 seq 基準
- **STATE_REQ（0x20）**：下學期，手臂狀態回傳

**未決**：ESTOP 誰能觸發、怎麼觸發（open-questions 16）；RESUME 後手臂直接衝向最新目標（F-29，W11 安全層處理）

### ⚠️ 規格模糊：JOINT 的 j6 是不是夾爪？

SO-101 是 5 關節 + 1 夾爪，但 JOINT 有 j1～j6，又另有 GRIPPER。j6 是夾爪的話 GRIPPER 重複，且兩者衝突時不知道聽誰的；j6 不是夾爪的話對應不到馬達。規格只寫「J1 為基座，往末端遞增」。

被問到：
> 「這是規格目前沒寫清楚的地方，我傾向 JOINT 只用 j1～j5，夾爪統一走 GRIPPER，會在下一版規格明確定義。」

**meeting 後**：記進 open-questions.md 給 B 的欄位，定案後升 v1.3（依 C-23 不改寫 v1.2）。

### 被問到

- 「為什麼標頭湊成 20 bytes？」→ 見下方「標頭 20 B 的原因」
- 「為什麼 seq 要 4 bytes？」→ 1 或 2 bytes 幾分鐘就繞回來，4 bytes 要一年多
- 「magic 有什麼意義？」→ `0x5343` 是 ASCII「SC」；little-endian 送，線上是 `43 53` 讀起來是「CS」（F-27，附錄）

### 標頭 20 B 的原因（對齊）

| 位移 | 欄位 | 大小 |
|---:|---|---:|
| 0 | magic | 2 |
| 2 | version | 1 |
| 3 | cmd_type | 1 |
| 4 | seq | 4 |
| 8 | timestamp_us | 8 |
| 16 | payload_len | 1 |
| 17 | reserved | 3 |
| 20 | payload 開始 | |

- 有用的欄位只有 17 bytes，reserved 補 3 bytes 湊成 20
- CPU 讀多 byte 數值時要位址是其大小的倍數（對齊）才一次讀完；沒對齊在 PC 上變慢，部分 ARM MCU（Cortex-M0 等級）會直接硬體錯誤
- seq 在位移 4、timestamp 在位移 8、payload 在位移 20，全部對齊；JOINT 的 6 個 int32 也都對齊
- 好處：接收端可以把緩衝區直接當結構指標讀（§7 的 `#pragma pack` 結構），不用逐欄搬
- 為什麼不是 24：payload 最大型別是 int32，4 bytes 對齊就夠
- reserved 也留給擴充（C-21 曾考慮放 session ID，後來沒採用）
- 注意（rationale §2.1）：接收緩衝區本身的起始位址也要對齊；STM32 上不確定就用 `memcpy`

> 「有用的欄位只有 17 bytes，補 3 bytes reserved 湊成 20，讓 payload 從 4 的倍數位址開始，接收端可以直接用結構指標讀；那 3 bytes 也順便留給以後擴充。」

### 一句話版本

- POSE：「直接給夾爪的空間座標，需要 IK 換算，下學期才實作，但格式先定好。」
- ESTOP／RESUME：「急停後鎖住位置、拒絕移動指令，直到解除；誰能觸發還要三人一起決定。」
- NOP：「空封包，告訴控制層連線還在，避免 watchdog 誤判斷線。」

## P7　修正也要再覆核（約 1 分鐘）★ 第二部分重點頁

**核心訊息**：工作方法，修正完的東西也要再檢查一次，而且是在實作前發現的。

照三個色塊由左到右：

> 「但再覆核一次 v1.1，發現第二個問題 F-26：time_ns() 跟 time() 讀的是同一個時鐘，只差回傳整數還是浮點數。Windows 上 Python 3.12 以前解析度只有約 15.6 ms，比我要量的幾毫秒迴路還粗。所以 v1.2 規定 Python 3.13 以上，不然用 ctypes 直接呼叫高精度 API。」

> 「F-26 是藏在 F-22 修正文字裡的錯誤。改完沒有再看一次，W12 量出來的數字還是不能用。我自己的 LeRobot 環境就是 Python 3.12，所以這不是紙上談兵。」

- 收尾那句是整頁重點：修正本身也要覆核，而且在實作前發現
- 表格不用念，指一下「若沒發現」那欄
- 15.6 ms 要跟「幾毫秒的迴路」放在一起講：量測工具的誤差比被量的東西還大

### 名詞

- **牆鐘時間**：電腦顯示的現實時間；同一台電腦所有程式讀的是同一個，可以互相比較。缺點是會被網路對時（NTP）調整，不適合量同一程式內的精確間隔
- **Unix epoch**：時間起算點 1970-01-01 00:00:00 UTC。時間戳 = 從那時起過了多少秒（git log 的 `1793801563` 就是）；規格用微秒版本放進 8 bytes 的 `timestamp_us`
- **QPC（QueryPerformanceCounter）**：Windows 高精度計數器，像馬錶，起點是開機，精度優於 1 µs，不受對時影響；數字只代表開機後過多久，跟現實時間無關
- **解析度 15.6 ms**：時鐘每 15.6 ms 才跳一次，中間發生的事都算成同一個時間

F-22 的直覺例子：
```
t0（牆鐘，從 1970 算）= 1,793,826,000,000,000 µs
t1（QPC，從開機算）   =             3,600,000,000 µs
t1 − t0 = 巨大的負數 → 是起點差，不是延遲
```
像一個人用西元年、一個人用「出生後第幾天」記時間，相減沒意義。

C-15 補充：同一程式**內部**量間隔（例如單包 UART 來回）仍可用 QPC，反而更準。

### ⚠️ 被追問時不要講過頭

文件寫「QPC 跨行程相減沒有意義」稍微說太滿：QPC 本身在同一台 Windows 上是全系統共用的。真正的問題是 Python `perf_counter` 官方不保證起點，且換到兩台電腦就不成立。F-22 的核心（一端牆鐘、一端 QPC，起點不同）與結論都不變。精確說法：

- 右下 Seeed 連結：若是實際參考的教學，講一句「安裝參考 Seeed Studio 的教學」；若是下週接手臂才用，這頁不用提
- 重點放在第 2 步（兩套環境分開）和第 5 步（模型要轉格式），其他快速帶過

### 名詞

- **conda**：Python 的環境管理員兼套件安裝工具。為每個專案建獨立環境（像不同抽屜），套件版本互不干擾（問題 #3 就是版本打架）。跟 pip 的差別：conda 還能裝非 Python 的程式（ffmpeg、CUDA 函式庫）
- **Miniforge**：conda 的精簡安裝程式，只裝 conda 本體，預設用社群的 conda-forge，沒有授權問題
- **ffmpeg**：處理影片／音訊的 C 程式。LeRobot 錄資料時把相機畫面壓成 mp4、訓練時解碼、評估時錄影（那 10 支 `eval_episode_*.mp4` 就是它產生的）。不是 Python 套件，用 `conda install ffmpeg` 裝
- **editable 模式（`pip install -e`）**：直接用 clone 的原始碼安裝，改原始碼不用重裝，方便讀程式、查 bug
- **PushT**：2D 模擬任務，控制圓點把 T 型方塊推到目標位置
- **diffusion policy**：模仿學習模型，學人類示範的動作；官方有 PushT 預訓練版本
- **processor 格式**：新版 LeRobot 把正規化參數從模型拆成獨立檔，舊模型要先轉換

### 被問到

- 「為什麼用 Windows 不裝 Ubuntu？」→ C 驅動 PC 端本來就是 Win32；LeRobot 在本專題是團隊保底與對照基準，這次的 Windows 問題都有解法。之後錄資料或訓練一直卡住，再考慮只把訓練放 Linux
- 「下週還要裝什麼？」→ 同一環境加裝 `[feetech]` 馬達驅動，在家就能先裝

### 一句話版本

- conda：「Python 的環境管理工具，讓 LeRobot 的套件版本不會跟其他專案打架。」
- ffmpeg：「處理影片的工具，LeRobot 錄資料、訓練和評估都要用它處理相機影片。」

### 延伸說明：editable、PushT、diffusion policy

**editable 模式**
- 一般安裝：pip 複製一份到套件資料夾，改原始碼不會生效
- editable：只建連結指向 clone 的資料夾，Python 直接讀那裡的原始碼
- `pip install -e ".[diffusion]"`：`.` 是目前資料夾，`[diffusion]` 是額外的套件群組（漏裝就是問題 #5）
- 好處：讀原始碼（F-25 要對照 `modeling_diffusion.py`）、加 print 除錯存檔即生效、`git pull` 更新、`git rev-parse` 查 commit（V-19）

**PushT**
- 2D 推方塊任務，出自 2023 年 Diffusion Policy 論文，模仿學習的標準測試
- 影片裡：藍色圓點是機器人、灰色 T 是要推的方塊（有碰撞與摩擦）、綠色 T 是目標、紅色十字是模型這一步給的目標點
- 成功：方塊與目標重疊率 ≥ 95%
- 為什麼用它：不需硬體；需要接觸、繞到對的一邊，難度剛好；observation → policy → action 結構跟實體手臂一樣

**diffusion policy**
- 模仿學習模型：看人類示範學「看到這畫面該怎麼動」
- 方法跟 AI 生圖（Stable Diffusion）一樣，生成的是動作：隨機雜訊 → 看最近 2 幀畫面逐步去雜訊 → 合理的動作序列
- 優點：能處理多種正確解法（從左推或從右推），不會把兩個答案平均成撞向中間
- 代價：去雜訊要跑很多步、推論慢，所以預測 16 步執行 8 步（F-25 action chunking），控制週期不均勻

**PyTorch（第 4 步）**
- Meta 開發的深度學習框架，用 Python 寫 AI 模型：tensor 運算、自動算梯度、一行搬到 GPU
- LeRobot 建在 PyTorch 上：diffusion policy 的結構、載入權重、推論、訓練都是它在算
- 層次：LeRobot → PyTorch → CUDA（NVIDIA 顯示卡運算平台）→ 顯示卡
- 為什麼換 CUDA 版：pip 帶進來的可能是只能用 CPU 的版本，diffusion policy 推論要去雜訊很多步，CPU 太慢；重裝時加 `--force-reinstall` 就是問題 #3 的起因
- 一句話：「PyTorch 是 LeRobot 底層跑 AI 模型的框架；預設可能只能用 CPU，所以我換成 CUDA 版，讓模型在顯示卡上跑。」

**一句話版本**
- editable：「直接用原始碼安裝，改了就生效，方便我讀和改 LeRobot 的程式。」
- PushT：「2D 推方塊的模擬任務，重疊率 95% 以上算成功，是模仿學習的標準測試。」
- diffusion policy：「用類似 AI 生圖的去雜訊方法生成動作，能處理多種正確解法，但推論慢，所以一次預測一串動作。」

### 各問題

| # | 錯誤 | 原因 → 解法 |
|---|---|---|
| 1 | conda 找不到 | 電腦沒裝 → 裝 Miniforge |
| 2 | git clone 沒權限 | 停在系統資料夾 → `cd ~` |
| 3 | numpy／fsspec 衝突 | `--force-reinstall` 連依賴一起升 → 指定版本降回 |
| 4 | `forkserver` 不支援 | 預設平行跑模擬環境 → `--eval.use_async_envs=false` |

### 名詞

- **`pip check`**：檢查環境裡有沒有版本衝突
- **Hugging Face Hub**：放 AI 模型與資料集的網站，`lerobot/diffusion_pusht` 是模型名稱

### 可用的模型 = 權重 + config + 正規化統計值（F-24）

- **權重**（`model.safetensors`）：訓練調出的幾百萬個數字，模型學到的知識
- **config**（`config.json`）：結構說明書，輸入幾張圖、哪些感測值、輸出幾維、`horizon: 16`、`n_action_steps: 8`。缺了就是 #8
- **正規化統計值**：訓練資料中每個輸入輸出的範圍（平均/標準差或最小/最大）。模型內部只認縮放到約 -1～1 的數字：輸入前縮放、輸出後換回實際值。新版另存成 processor 檔，就是 #7
- 比喻：只會用公分思考的廚師，權重是廚藝、config 是菜單格式、統計值是台斤換公克的換算表；換算表錯了，廚藝再好也會放錯量
- **為什麼重要**
  1. 三樣錯一樣，成功率會趨近 0，所以 7/10 能證明三樣都載入正確（P10）
  2. 統計值來自訓練資料，PushT 是圓點 2D 範圍、SO-101 是 6 顆馬達角度與相機影像；換手臂、重新校正、換相機位置都會變，所以實體手臂要用自己錄的資料訓練（P11「模型」那列）

> 「模型不只是訓練出來的權重，還要有描述結構的 config，和把感測值縮放到模型懂的範圍的統計值；統計值來自訓練資料，所以換手臂或相機，舊模型就不能直接沿用。」

### 名詞

- **snapshot.py**：10/11 寫好的工具，只讀不寫，存下每顆馬達的暫存器，也量 READ 往返時間
- **find-port**：LeRobot 找手臂接在哪個 COM 埠
- **calibrate**：LeRobot 校正，記錄關節零點與範圍，會寫入馬達暫存器
- **teleoperate**：遙控模式，人動 leader，follower 跟著做
- **echo**：轉接板把送出的封包回送，協定上完全合法，會被誤當成馬達回應（F-20）
- **hal_win32.c**：驅動的 Windows 版硬體抽象層，開序列埠、收送 bytes
