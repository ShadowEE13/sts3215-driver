## 上層介面（11/03 定案）

### 傳輸方式：UDP

對 A、B 公開固定的 UDP port 與封包格式。選 UDP 而非 TCP 的理由：控制迴圈的資料會過期，掉包時要的是下一包而非重傳舊值；TCP 的可靠性與 head-of-line blocking 對控制流是錯的行為。此權衡與 STS3215 的「WRITE 等回應包、SYNC WRITE 不等」完全同構。

跨語言亦無痛：C# `UdpClient`、Arduino `WiFiUDP`、C `sendto/recvfrom` 皆為標準庫。三邊（Arduino AVR/ARM、x86 C#、C 驅動）均為 little-endian，與 STS3215 一致，零轉換。

### 隊友環境

| | 平台 | 接入方式 |
|---|---|---|
| A（VR 顯示） | Unity / C# | 同機 localhost UDP |
| B（手部感測） | Arduino / C++ | 板子有 WiFi → 直接送 UDP；無 WiFi → B 自行寫序列埠轉 UDP 的橋接程式 |

**B 的接入由 B 負責。** 本驅動不直接讀 Arduino 的 USB 序列埠——那會把驅動與 B 的硬體綁死，且測試時必須借用他的裝置，違背介面凍結的用意。

### 封包格式（草案，待定稿後發出）

**指令包（B → 驅動），24 bytes**

| 欄位 | 長度 | 說明 |
|---|---|---|
| magic + version | 2 | 封包辨識與版本 |
| CmdType | 1 | 0x01 關節角度 / 0x02 末端座標 / 0x03 預留（原始感測值） |
| flags | 1 | 急停、扭矩開關 |
| seq | 4 | 序號，丟棄亂序與統計掉包 |
| timestamp | 4 | 送出時間（µs） |
| payload | 12 | 六軸角度（6 × int16）或末端姿態 |

**狀態包（驅動 → A、B），32 bytes**：六軸當前位置、error byte、溫度與負載旗標、本端時間戳，並**原封回傳收到的 seq 與 timestamp**。

回傳 seq 與 timestamp 讓端到端延遲量測免費取得——A 收到狀態包時以自身時鐘減去其中的 timestamp 即為完整一圈延遲。此為 W12 的交付項目，欄位現在留好，屆時無須改協定。

### 目標控制頻率

100 Hz（暫定）。依文獻推算：latency timer 維持預設 16 ms 時上限僅 50–60 Hz，調至最低才有 300 Hz 量級，故 100 Hz 為誠實且有餘裕的目標。

手臂僅一組、留在實驗室、採預約制。原則：**凡需真機者集中同場完成，其餘一律在家做。**

4. 實測 `0x07` 回應延遲是否可改、latency timer 實際值
5. 單包 WRITE/READ 往返時間量測
6. 六軸在真實負載下的穩定性

第 2 項是把稀缺的實驗室時間換成可無限重用的資產。

**在家可做**：模擬器、驅動實作、介面文件、六軸封包邏輯、測試、報告、STM32 side project。
