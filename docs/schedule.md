**更新日期**：2026/10/11

## 優先級調整（10/11，與教授及實驗室學長討論後）

學長的意見：三人應優先各自讓自己的部分「能運作」，下學期才對接。因此先用 LeRobot 把手臂跑起來，C 驅動優先級往後。學長並未否定 C 驅動的價值，只是順位問題。

**本規劃的回應方式**：把「團隊保底線」與「個人交付物」分開處理，兩者不互斥。

| | 內容 | 由什麼滿足 |
|---|---|---|
| 團隊保底線 | 手臂會動、程式呼叫得到、介面已定義 | LeRobot（第一版後端） |
| 個人交付物 | 自製 C 驅動、安全層、延遲量測 | 本子題目本體（第二版後端） |

關鍵做法是**介面凍結**：對 A、B 公開一組固定介面，背後第一版用 LeRobot 實作，第二版換成自製 C 驅動，對隊友完全無感。這與 HAL 分層是同一個思維，只是往上提一層——

```
      A / B（隊友）
           ↓ 凍結的上層介面（含 CmdType）
   ┌───────┴───────┐
LeRobot 後端      C 驅動後端
（第一版，保底）   （本子題目成果）
```

做完介面凍結，C 驅動何時完成都不會卡到任何人，學長的顧慮即消解。

此外，先跑通 LeRobot 並非延後 C 驅動，而是它的**前置條件**：W6–7 硬性檢查點所需的「已知正確參考封包」正是由 LeRobot 送出並擷取而來。兩者順序本來就一致。

## 硬承諾與彈性項目

優先級調整後，整體採「走到哪算到哪」，但**保留一個硬承諾**：

> **10/25（W7 結束）前，C 驅動完成單軸 READ/WRITE。**

理由：單軸讀寫是子題目成立與否的分界線。有它，題目是「實作驗證」；沒有它，題目實質變成「用現成函式庫跑通手臂」，與選擇此分工的理由（嵌入式作品集、韌體方向）背道而馳。沒有日期的目標在學期中段通常會歸零——手臂借到了、團隊要整合了、報告要寫了，C 驅動永遠是「下週再說」。

- 六軸同步的最佳化與 SYNC WRITE 效益評估
- latency timer 與延遲調校的完整實驗（A/B/C 三組對照）
- 模擬器的故障注入進階功能

## 實驗室場次與家中工作的切分

手臂只有一組、留在實驗室、採預約制，因此實驗室時間是最稀缺資源。原則：**凡是需要真機的事情集中在同一場次做完，其餘一律在家做。**

**只有真機能做（進實驗室時優先）**
1. 跑通官方 LeRobot 範例，建立「已知可運作」基準
2. 擷取 PING／READ／WRITE 三種參考封包並存檔 ← 第 1 項成功後幾乎免費，務必同場完成
3. 核對兩組電源標示與馬達型號
4. 實測 0x07 回應延遲是否可改、latency timer 實際值
5. 單包 WRITE/READ 往返時間量測

第 2 項是把稀缺的實驗室時間換成可無限重用的資產：封包存成檔案後，在家就能一直拿來比對驗證。

**在家可做**
- 介面凍結文件撰寫
- C 驅動實作（封包組裝、checksum、parser、狀態機）
- 模擬器實作（見 `sim-spec.md`）
- 文獻、報告、STM32 UART/GPIO 預習（板子已帶回家）
