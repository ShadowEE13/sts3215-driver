### W13 的方向改變（F-36、F-37）

原規劃是驗證文獻推算的兩個延遲瓶頸。11/19 實測後**兩個都不存在**：

- `0x07` 回應延遲：全新套件馬達出廠即為 0，不是規格書的 250（500 µs）→「六顆佔 3 ms、頻率掉到 260 Hz」對泛用 STS3215 成立，對本套件不成立（F-36）
- latency timer：轉接板是 WCH CH343P 不是 FTDI，無 echo，READ RTT 中位數僅 0.34–0.63 ms → FTDI 的 16 ms 瓶頸不適用（F-37）

**這不是分析錯誤，是實測否證了前提。** 推算在它的前提下正確，報告寫起來反而更強：有預測、有量測、有落差的解釋（規格書寫 250、FD 標 Reserved、LeRobot 當它存在，三方說法不一）。

W13 因此改為：**確認瓶頸不在，並量出真正的限制在哪**——Python 迴圈開銷、USB 排程、還是 rustypot 那層。以 RTT 0.4 ms 的量級推，六軸一個週期約一兩毫秒，100 Hz 有相當餘裕，所以「什麼限制了上限」比原本的 A/B 對照更有價值。

latency timer 的 A/B 對照若仍要做，需另找一塊 FTDI 轉接板當對照組（可問學長實驗室有無）。

### W13 的實驗設計（C-41）

11/25 第三次 meeting，教授建議下週做幾個定量實驗（例如待機、特定任務），把圖表畫出來。

**這不是轉向，是同一個問題的更紮實做法。** W13 本來就要找 73.49 ms 長尾的成因（F-59），
原本打算在程式裡打時間戳；現在變成有對照組、有圖表的正式實驗。

#### 四個條件

| 代號 | 條件 | 目的 |
|---|---|---|
| A | 待機：迴圈照跑，人不動 leader | 基準線。分離通訊與機構運動 |
| B | 單軸緩慢移動 | 最小運動量 |
| C | 六軸正常遙控 | 對應 W12 的 688 秒 |
| D | 負載：夾持物體或手臂伸直 | 電流拉高時通訊會不會變差 |

各跑 **180 秒**（約 11000 個週期，目標 60 Hz）。樣本數要夠才看得出 p99.9 的形狀——
1000 個 tick 只會有 1 個點落在 p99.9，看不出分布。

**關鍵設計：四個條件共用同一段程式碼**，`--condition` 只是標籤，不改變任何行為。
程式路徑一致，唯一的變數才是物理條件，對照才成立。

因此「待機」的定義是：**迴圈照常跑 observe / teleop / send，匯流排流量與 C 完全相同，
只是人不去動 leader**。若待機時也出現 73 ms 長尾，就直接證明長尾與運動無關。

#### 第五個對照組：fake

`--port fake` 不碰硬體、不 import LeRobot。它不只是驗證 logger 本身，
更是「這台電腦有多少抖動」的對照組：

- fake 也有 73 ms 尖峰 → 長尾完全在主機側，與手臂無關
- fake 只有數 ms、真機 73 ms → 差額才是硬體路徑（USB／驅動）造成的

11/27 在容器上試跑：假裝置的 send 段寫死 0.21 ms，p50 量到 0.211 ms 但 **max 5.661 ms**。
沒有匯流排、沒有馬達、沒有 USB，尖峰照樣出現。這個對照組要在實際要做實驗的那台 Windows 上跑。

#### 四張圖

| 圖 | 回答什麼問題 |
|---|---|
| ① 延遲分布直方圖（y 軸取 log） | 為什麼平均 1.14 ms 卻最差 73.49 ms——分布長什麼樣 |
| ② 百分位數 p50／p90／p99／p99.9／max | 取代「平均／最差」。「p99 = 2 ms」比平均值有說服力 |
| ③ **延遲對時間的散點圖** | **長尾的成因**。診斷力最強的一張 |
| ④ 四條件箱型圖並排 | 負載與運動會不會影響通訊 |

③ 的**形狀本身就是診斷**：
尖峰等間隔出現 → 作業系統或 USB 的排程週期；
隨機散布 → 驅動層的重試或逾時；
集中在開頭 → 暖機或快取未命中。

這張圖可能直接回答 W13 的核心問題，**不需要邏輯分析儀**（見 W12 簡報 P7 的推算）。

#### 工具

`tools/cadence.py`（11/27 完成）。設計要點：

- 迴圈中不寫檔、不配置記憶體、不做單位換算。全部進預配置的 numpy 陣列，跑完才一次寫出。
  用有緩衝的檔案物件會在緩衝滿時自動 flush，製造出等間隔尖峰——那正是要找的 OS 排程特徵，
  會得到自信但錯誤的結論。
- 記錄**絕對的 `t_start_ns`**，否則無法區分「迴圈自己慢」（work 變大）與「迴圈被 OS 搶走」
  （work 正常但 t_start 間隔變大）。兩者平均週期相同、成因不同。
- 溫度每 10 秒讀一次會多一筆匯流排交易（fake 實測 work 從 2.6 ms 升到 3.4 ms），
  該週期以 `temp_read` 標記並在統計時排除，否則每 600 個 tick 污染一個樣本，
  剛好落在最在意的尾端。

## Python 系統的五步路徑

詳見 `lab-log/week10.md` 第四節。關鍵是**前四步完全不需要硬體**，與當初做模擬器同一個思路。

| 步 | 內容 | 驗證方式 | 需硬體 |
|---:|---|---|---|
| 1 | 綁 49200、收 UDP、印 hex | 用 `interface-spec.md` §7 的發送端當訊號源；應收到 46 bytes | 否 |
| 2 | 拆標頭、驗 magic/version/CRC、印六軸角度 | 對照 §2.3 的 NOP 範例封包與 CRC 檢查值 `0x29B1` | 否 |
| 3 | 固定 100 Hz 主迴圈 + 抽乾佇列只留最新一包 | 量測實際週期抖動 | 否 |
| 4 | 安全層 + 假手臂（二十行 dict） | 送越界角度、壞 CRC、停送 300 ms、送 ESTOP | 否 |
| 5 | 假手臂換成真的 LeRobot bus | 真機 | **是** |

規模約 150–250 行，單一檔案。**不碰** asyncio、多執行緒、類別繼承、numpy、任何框架。

要學的只有三樣：`socket` 的 UDP 收送、`struct` 的 pack/unpack、固定頻率主迴圈，各約一小時。
