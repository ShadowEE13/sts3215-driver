# interface-spec 設計理由

> 對應 `interface-spec.md` v1.2。規格寫「是什麼」，這份寫「為什麼」。

## 為什麼需要這份規格

這份規格要解決的是分工問題：

```
B 的橋接程式  ──(凍結的封包格式)──▶  C 的控制層
                                      ├─ 第一版：LeRobot（保底）
                                      └─ 第二版：自寫 C 驅動（專題成果）
```

只要封包格式不變，B 可以照自己的進度開發，控制層也可以隨時換掉後端，雙方都不用等對方。所以這份文件寫得特別嚴格：一旦交出去，改動就會影響隊友。

## 逐節的設計理由

### §1 UDP 而不是 TCP

- 控制資料會過期。掉了一包，要的是下一包的新位置，不是 30 ms 前的舊位置。
- TCP 會重傳，而且有 head-of-line blocking：一包沒到，後面已經到的封包全部卡住。這對控制流是錯誤的行為。
- 位址用 localhost，因為 B 的橋接程式和控制層跑在同一台電腦。

### §2.1 標頭的每個欄位

| 欄位 | 用途 |
|---|---|
| `magic` | 確認收到的是這個協定的封包，不是別的程式誤送到同一個 port 的資料 |
| `version` | 不相容的改版用這個區分。舊版程式收到新版封包會直接拒絕，而不是解錯 |
| `cmd_type` | 一個 port 承載多種指令，以後加指令不必開新 port |
| `seq` | 判斷封包是否過期或亂序、ACK 對應是哪一包、統計掉包數 |
| `timestamp_us` | W12 量延遲的唯一依據 |
| `payload_len` | 讓不同指令有不同長度的 payload，也能檢查長度 |
| `reserved[3]` | 預留空間：以後做相容的擴充時，不必改標頭大小 |

**為什麼是 20 bytes**：讓 payload 從 4 的倍數位置開始，C 端可以直接用結構指標讀，不必逐欄搬移。另外 `timestamp_us` 剛好在 offset 8，這個 8-byte 欄位也是對齊的。

**`magic` 為什麼要以 uint16 比對**（v1.2）：v1.1 把 `0x5343` 註解成 ASCII `"SC"`，但全欄位 little-endian，線上的 bytes 其實是 `43 53`，也就是 `"CS"`。兩份參考實作（§7 的 Python 和 C 結構）都用數值，彼此一致；會出錯的是照註解自己寫的人，例如 B 直接寫 `b"SC"`。數值不改，因為 B 已照 v1.0 開發，改數值就是不相容變更；改成在規格裡寫清楚線上的 bytes。

**實作注意**：在 STM32 上用 `#pragma pack(1)` 的結構指標去讀接收緩衝區，還要看緩衝區本身的位址有沒有對齊。改用 `memcpy` 會比較保險。這不影響封包格式，只是實作時要注意。

### §2.3 localhost 為什麼還要 CRC

- UDP 本身有檢查碼，但作業系統在回送介面上可能略過驗證。
- 更重要的目的不是防傳輸錯誤，而是在整合階段抓到兩端格式不一致。B 的結構如果多一個 byte、或少做一次對齊，CRC 會立刻失敗，而不是等到手臂亂動才發現。
- 以後改走無線，這個欄位不用動就能直接用。
- CRC-16/CCITT-FALSE 是很常見的變體，各種語言都容易找到實作，可以互相對照。

**為什麼附驗證用資料**（v1.2）：CRC 有很多變體，初始值或反射設定差一點，算出來就不一樣，而且兩端都「看起來能跑」。標準檢查值（`"123456789"` → `0x29B1`）先確認演算法本身；完整的 NOP 封包再一次確認欄位順序、位元組序和 `magic`。兩端各自對過這兩組資料再整合，出錯時就知道是哪一層的問題。範例封包已用 §7 的 Python 範例和 §2.3 的 C 參考實作各算一次，結果一致。

### §2.4 時間戳的時鐘

這一節是 v1.1 補上的，起因是 F-22：

- v1.0 的 Python 範例用牆鐘時間，但 `system-comm.md` v0.3 寫控制層用 `QueryPerformanceCounter`。
- QPC 的起點是開機後的任意時刻。兩個起點不同的時鐘相減，得到的是起點差，不是延遲。

規定的做法：

- 兩端一律用 **Unix epoch 牆鐘微秒**。
- **Python 端**（B 的橋接，以及 C 第一版的 LeRobot）用 `time.time_ns()`：回傳整數，直接對應 uint64 欄位，不經過 float 換算。
- **Windows 上 Python 必須 ≥ 3.13。** 3.12 以前，`time.time()` 和 `time.time_ns()` 底層都是 `GetSystemTimeAsFileTime()`，解析度約 15.6 ms，比要量的數毫秒迴路還粗；3.13 起改用 `GetSystemTimePreciseAsFileTime()`，解析度優於 1 µs。用 `time.get_clock_info('time')` 確認。版本被卡住時，用 ctypes 直接呼叫 `GetSystemTimePreciseAsFileTime()`。
- **C 端（Windows）**用 `GetSystemTimePreciseAsFileTime()`。它回傳自 1601-01-01 起的 100 ns 刻度，換成 epoch 微秒：`(ticks - 116444736000000000) / 10`。不精確版的 `GetSystemTimeAsFileTime()` 同樣只有 15.6 ms，一併列為禁用。

15.6 ms 和實測 `select()` 精度約 15.6 ms 是同一個來源：Windows 系統計時器的節拍。

**v1.2 的修正**：v1.1 寫的是「用 `time_ns()` 不用 `time.time()`，因為 `time_ns()` 走高精度路徑」。這是錯的：兩個函式讀同一個時鐘，解析度一樣，差別只在回傳整數還是 float。15.6 ms 取決於 **Python 版本**，不是取決於用哪個函式。照 v1.1 做，在舊版 Python 上 W12 一樣會量不準，所以 v1.2 把條件改成版本要求。

### §3 指令類型

- **NOP**：心跳。B 沒有新資料時也要送，讓控制層知道 B 還活著。
- **POSE 先定義、本學期不實作**：逆運動學排在下學期，但先把格式凍結，B 現在就能照 POSE 開發，下學期接上 IK 就能用，介面不必再改。
- **GRIPPER 獨立出來**，用 0–10000 的正規化值：夾爪的幾何換算由控制層處理，B 只需要知道「開多少」。
- **ESTOP / RESUME**：急停要能從上層觸發。
- **STATE_REQ**：先佔一個編號，給下學期 L10 手臂狀態回傳用。

### §4 用整數定點數，不用浮點

- 兩端對數值的解讀完全確定，不會有浮點格式的歧異。
- 和伺服機暫存器一樣是整數。
- 以後橋接搬到沒有 FPU 的 MCU 上也不用改。

範圍綽綽有餘：int32 以 0.001 度為單位，可表示約 ±214 萬度；以 0.01 mm 為單位，約 ±21 公里。

### §5 回應預設關閉

- 控制流是 fire-and-forget，不需要逐包確認。開 ACK 只為了兩件事：開發時確認封包有被正確解析，以及量往返時間。
- 回應包不回傳原始時間戳，B 用 `acked_seq` 對回自己記下的發送時間就好，封包也比較短。

### §6 時序與失效行為

- **100 Hz、只取最新一包**：發送端比控制層快也沒關係，自然退化成「取最新」。
- **過期就丟、不重排、不重傳**：理由同 §1，過期的控制資料沒有價值。
- **watchdog 逾時後清除 `seq` 基準**（v1.2）：B 的橋接程式重開時，`seq` 會從頭算。只靠「小於等於就丟」的話，重開後的封包全部會被當成 STALE，要等新 `seq` 追上舊值才恢復，前一次跑多久就要等多久。開發期重開橋接程式是家常便飯，這會變成「手臂莫名其妙不動」的難查問題。解法放在控制層：STALE 不重置 watchdog，逾時就清除基準。這樣 B 不用改程式，也不必在封包裡加 session ID 這類欄位。
- **watchdog 是「保持」而不是「斷電」**：扭力一關，手臂會因自重垮下。所以這裡的「安全」是鎖住不動。
- **上電時先讀實際角度當目標**：避免一上電，手臂就從目前姿勢猛然跳到程式預設值。
