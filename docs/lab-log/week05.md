## 三、新發現

### 協定層（對照原始碼才發現，手冊未明載或有誤）

**F-01　負數採 sign-magnitude，非二補數**
最高位為方向位，其餘為絕對值。位置與速度在 BIT15，負載在 BIT10，位置校正在 BIT11。
例：−100 應送 `64 80`，若用二補數送 `9C FF` 會被解讀成極大的正值。
影響：單圈位置模式不會遇到，但讀取速度或負載時一旦反轉即出現。已寫入 C 版編解碼函式並編譯驗證。

**F-02　手冊 RESET 範例的 checksum 印錯**
手冊 1.3.9 印 `F6`，正確應為 `F2`。15 個範例封包中僅此一處錯誤。
影響：手算驗證時若以此為基準會誤判自己的實作有問題。

**F-03　LeRobot 的鮑率對照表與原廠不符**
設定值 5–7 兩邊不同（原廠 76800 / 57600 / 38400，LeRobot 為 57600 / 38400 / 19200）。
處置：以原廠記憶體表為準。預設 1 Mbps 不受影響。

**F-04　運行時間暫存器 0x2C 的用途已釐清**
位置模式下填 0，僅 PWM 開環模式使用。原廠 SDK 的 `WritePosEx` 從 0x29（加速度）起一次寫 7 bytes，涵蓋加速度、位置、時間、速度，比分開寫省兩個封包往返。

**F-05　Phase 暫存器 0x12 的 BIT4 影響位置回授範圍**
BIT4 = 1 時回授多圈角度，LeRobot 會主動清為 0 以強制單圈 0–4095。
影響：若未處理，位置讀值可能超出預期範圍或出現負值。

**F-06　LeRobot 的遙操作迴圈不檢查馬達回報的錯誤狀態**
`_sync_read` 僅檢查通訊結果，未讀取每顆馬達回應包中的 error byte（原廠 SDK 其實有保留該值）。另外 `max_relative_target`（單步幅度限制）預設為 `None`，即預設不啟用。
意義：這是本專題安全層可明確補足的部分，為期末報告的貢獻點之一。

### 電氣層

**F-07　扭力常數 Kt 經驗算自洽，可用電流推估扭力**

| 版本 | 堵轉扭力 ÷ 堵轉電流 | 額定扭力 ÷ 額定電流 | 規格書 Kt |
|---|---|---|---|
| 7.4V | 19.5 ÷ 2.50 = 7.8 | 5.0 ÷ 0.65 = 7.7 | 8 kg·cm/A |
| 12V | 30.0 ÷ 2.70 = 11.1 | 10.0 ÷ 0.90 = 11.1 | 11 kg·cm/A |

意義：安全層不需額外力感測器，讀暫存器 0x45 當前電流乘上 Kt 即可估算負載；反之亦可由扭力上限換算保護電流設定值。

**F-08　過載保護為三暫存器構成的鏈**
`0x24` 偵測（預設 80% 堵轉扭力）→ `0x23` 計時（預設 2 秒）→ `0x22` 降載（預設 20%）。
換算：leader 15.6 → 3.9 kg·cm；follower 24.0 → 6.0 kg·cm。
注意：保護觸發後扭力僅餘兩成，手臂會明顯軟掉，需能與通訊異常區分。

**F-09　兩版本工作電壓範圍不同，電源不可互換**
leader 4–7.4V，follower 4–14V。12V 接上 leader 會觸發過壓保護或損壞。風險不對稱：反向接只是扭力不足。

### 文獻

**F-10　舵機回應延遲不隨鮑率縮短**（Bestmann et al.）
鮑率提高四倍，傳輸時間變四分之一，但每顆馬達的回應延遲不變。馬達數多時此項成為主導。

**F-11　MCU 轉發封包反而比純 USB 轉序列慢**（Bestmann et al.）
STM32 解析封包本身成為瓶頸，提高鮑率與匯流排數皆無法成比例提升。
但：其架構為 MCU 當轉發器、PC 仍在控制迴圈內，與本專題規劃的 MCU 獨立控制不同，結論不可直接套用。

**F-12　USB 轉序列晶片的 latency timer 會主導小封包的延遲**（FTDI）
晶片需緩衝區滿 62 bytes 或 timer 逾時才回送資料。本系統單顆 READ 回 8 bytes、六顆 SYNC READ 回 48 bytes，**兩者皆填不滿**，故每次讀取都要等 timer。預設 16 ms 對應約 50–60 Hz；調至 1 ms 才有 300 Hz 量級。

**F-13　套用 Bestmann 模型估算本系統**
一個遙操作週期：SYNC READ(8+6) + 六個回應包(48) + SYNC WRITE(8+18) = 88 bytes → 1 Mbps 下為 0.88 ms。
若回應延遲暫存器 0x07 維持預設 500 µs/顆，延遲佔週期約 77%，頻率降至約 260 Hz。

**F-14　兩篇文獻皆未涵蓋 MCU 獨立控制的架構**
Bestmann 測的是各種經過 USB 的控制板，FTDI 講的是 USB 晶片本身。兩者皆未測試「PC 完全不在控制迴圈內」的組態。
意義：為第 14–16 週的 STM32 階段提供了研究上的正當性，使其從選修的練習轉為補足文獻缺口的對照組。

## 五、計畫變更

**C-01　實作語言由「C/C++」收斂為純 C11**
理由：STM32 移植時可免除 exceptions / RTTI / 靜態初始化順序等 C++ runtime 問題；瑞昱韌體職缺的程式碼庫以 C 為主；驅動層所需的抽象用 struct 裝函式指標即可達成。
配套：`-Wall -Wextra -Werror -Wconversion`、不使用 `malloc`、header 加 `extern "C"` 以利下學期與隊友的 C++／Unity 端整合。

**C-02　架構分層由第 8 週提前至第 5 週定案**
四層：Application / Device / Protocol / HAL。提前的理由是協定研讀時同步對照了實作，架構決策的依據已足夠。
影響：HAL 介面需在寫第一行 C 之前定好，而非第 14 週回頭重構。

**C-03　STM32 週邊預習由第 11–13 週零碎時間提前至現在**
理由：開發板已可攜回，而手臂無法攜出，在家時間本來就動不了真機。
影響：第 14–16 週可全數用於移植本身。

**C-04　新增虛擬馬達模擬器作為測試工具**
手臂需預約且不可攜出，故建立純軟體模擬器以利在家開發。定位為測試基礎設施，非交付的驅動本體。規格見 `docs/sim-spec.md`。
附帶價值：模擬器可注入真機難以製造的故障（不回應、錯誤 checksum、強制 error byte、雜訊），並驗證「Protocol 層能否脫離硬體測試」這項架構驗收標準。

**C-05　新增 A / B / C 三組對照實驗**
由 F-14 推導。A：PC + USB，latency timer 預設；B：PC + USB，timer 調至最低；C：STM32 獨立控制，無 USB。前二者排於第 11–13 週，C 組於第 14–16 週（條件性）。

**C-06　構想：以 STM32 扮演假馬達，進行硬體在環測試**
純軟體模擬器測不到真實時序。若讓 F401RE 依協定回應封包，在家即可量測真實序列埠往返時間，提前驗證 F-12 的 latency timer 問題。
附帶價值：撰寫此假馬達所需的 UART / DMA / 方向控制，與第 14–16 週移植所需的技術完全相同，等於將預習與測試工具合併。
狀態：構想階段，待 V-11、V-12 確認後評估。
