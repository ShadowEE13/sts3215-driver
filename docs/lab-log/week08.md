## 四、新發現

**F-26　`time.time_ns()` 和 `time.time()` 讀的是同一個時鐘，15.6 ms 是 Python 版本造成的（更正 F-22、C-16）**
`week07` F-22 第二段和 C-16 寫「不用 `time.time()`，解析度不足」，v1.1 §2.4 更進一步寫「`time_ns()` 走高精度路徑，解析度在 µs 以下」。這是錯的。CPython 的這兩個函式讀的是同一個系統時鐘，差別只在回傳整數還是 float。在 Windows 上，解析度取決於 Python 版本：3.12 以前的底層是 `GetSystemTimeAsFileTime()`，約 15.6 ms；3.13 起改用 `GetSystemTimePreciseAsFileTime()`，優於 1 µs（見 CPython 3.13 的更新說明，gh-63207）。
影響：照 v1.1 去做的話，如果 B 或 LeRobot 的環境是 3.12 以前，換成 `time_ns()` 一樣是 15.6 ms 才跳一次，W12 量不出只有數毫秒的迴路延遲。
為什麼會錯：把「函式不同」當成「時鐘不同」，沒有查到底層實作。F-22 的修正文字寫完之後也沒有再被覆核。
處置：C-19。

**F-27　`magic` 的註解和位元組序互相矛盾**
v1.1 寫 `magic = 0x5343（ASCII "SC"）`，同時又規定所有欄位都是 little-endian。`0x5343` 以 little-endian 送出時，bytes 是 `43 53`，用 ASCII 讀是 `"CS"`。
§7 的 Python 範例（`struct.pack("<H", 0x5343)`）和 C 結構都用數值，彼此一致，所以照範例寫不會出錯。會出錯的是照註解自己實作的人，例如 B 直接寫 `b"SC"`，接收端解出來是 `0x4353`，就會判成 `BAD_VERSION`。這種錯誤在 localhost 上很難查，因為封包確實有送到，只是全部被拒絕。
處置：C-20。

**F-28　發送端重啟時，`seq` 規則會讓手臂一直鎖住**
§6.2 規定：`seq` 小於或等於已接受的最新值，就丟棄。B 的橋接程式重開之後，`seq` 從 1 開始算，所有封包都會被判為 `STALE`，手臂一直停在保持狀態，直到新的 `seq` 追上舊值。前一次跑了一小時（100 Hz 下約 36 萬包），就要再等一小時。v1.1 也沒有規定被判為 STALE 的封包算不算 watchdog 所說的「合法封包」。
為什麼原本沒想到：§6.2 只考慮了穩定運作時的亂序和過期，沒有考慮程式的生命週期（重啟）。開發期間重開橋接程式是家常便飯，不處理的話，就會變成「手臂莫名其妙不動」這種很難查的問題。
處置：C-21。

**F-29　watchdog 恢復或 `RESUME` 之後，手臂會直接移向最新目標（未決）**
watchdog 保持或急停期間，操作者的手可能已經移動了。恢復後收到的第一包就是新位置，手臂會以設定速度一次移過去，而不是從保持的位置平順地接上。
處置：這次不改規格，等 W11 設計安全層時一併決定，例如恢復後限制每個週期的目標變化量。

## 六、計畫變更與決策

**C-19　Windows 上的 Python 必須 ≥ 3.13，否則以 ctypes 呼叫 `GetSystemTimePreciseAsFileTime()`（11/05，修正 C-16）**
起因：F-26。
決定：
- B 的橋接和 C 第一版（LeRobot）都用 `time.time_ns() // 1000`，前提是 Windows 上的 Python ≥ 3.13，並以 `time.get_clock_info('time')` 確認
- 如果環境被套件卡在舊版，就以 ctypes 直接呼叫 `GetSystemTimePreciseAsFileTime()`，換算方式和 C 端相同
- C 第二版（自製 C 驅動）的做法不變；非 Precise 版的 `GetSystemTimeAsFileTime()` 一併列入禁用
- 繼續用 `time_ns()` 而不用 `time.time()`，但理由改成：`time_ns()` 回傳整數，可以直接對應 uint64 欄位，不經過 float 換算

理由：要求版本是最簡單的寫法；ctypes 版本留給版本被鎖住的環境。兩種寫法呼叫的是同一個 API，取到的時間可以直接相減。
C-16 的其他部分（使用 Unix epoch、禁用 QPC 和 `perf_counter`）仍然成立。

**C-20　`magic` 數值不變，只改註解（11/05）**
起因：F-27。
考慮過的選項：
1. **只改註解**：數值維持 `0x5343`，寫明線上 bytes 是 `43 53`，並規定以 uint16 比對
2. 數值改成 `0x4353`：線上 bytes 讀起來就是 `"SC"`，看 hex dump 比較直觀

決定：選 1。
理由：B 已經依 v1.0 開發，照 §7 範例寫的程式本來就是對的。選 2 是不相容變更，B 必須改常數，換來的只是 hex dump 比較好讀。介面凍結（C-07）的意義就在這裡：遇到這種取捨，要偏向不動格式。

**C-21　watchdog 逾時後清除 `seq` 基準；STALE 封包不重置 watchdog（11/05）**
起因：F-28。
考慮過的選項：
1. **只改控制層**：STALE 封包不重置 watchdog，逾時就清除基準，下一個合法封包不論 `seq` 是多少都接受
2. 用 `reserved` 欄位放 session ID：B 每次啟動換一個值，控制層看到新的 ID 就重設基準
3. 先記進 `open-questions.md`，之後再和 B 討論

決定：選 1。
理由：只要改接收端，B 不需要配合。重啟後最多 200 ms 就會恢復，而 Python 程式重開本來就要比這更久，使用者感覺不到。選 2 需要 B 改程式，還要多佔一個欄位；選 3 等於讓一個已知的整合陷阱留到整合時才出事。
代價：如果 B 在 200 ms 內就重開完成，這段時間內的封包會被丟掉。但仍然最多 200 ms 就會恢復，可以接受。

**C-22　規格附上驗證用資料，兩端在整合前先各自對照（11/05）**
CRC 有很多變體，初始值或反射設定只要差一點，兩端都「看起來能跑」，卻互相不認得對方的封包。§2.3 因此附上 CRC 標準檢查值和一個完整的 NOP 封包：前者確認演算法，後者一次確認欄位順序、位元組序和 `magic`。整合時如果出錯，可以先判斷是哪一端、哪一層的問題。
這和驗收 A/B 是同一個原則：用外部參照來驗證，而不是只讓兩端互相對照（見第三節「驗證強度的限制」）。

**C-23　已交付的文件用新版號修正；lab-log 不回頭改寫（11/05）**
- 規格：v1.1 已經 push，也可能已經交給 B，所以不改寫 v1.1，而是升為 v1.2 並寫入變更紀錄。版本號是 B 唯一能察覺「規格變了」的訊號
