## 二、方向調整的理由與範圍

### 2.1 理由（三人共同決定，11/15）

- **團隊優先讓手臂能用**。手臂即將存在，但三人各自的部分都還沒接上。先有一個能跑的系統，整合才有對象
- **以現有工具為主**。LeRobot 與飛特 SDK 是成熟的實作，重寫一遍不會產生新的價值
- **自我評估**：底層 C 的實作在目前的程度下難以獨力理解並完成，即使有 AI 協助。與其把時間放在看得懂但寫不出來的部分，不如先建立一個完全講得出來的系統

第三點是這次調整的核心。相關的判斷見 2.3。

### 2.2 這不是推翻 C-07，是把它提前

C-07 原本的安排是：第一版後端用 LeRobot（團隊保底），第二版換自製 C 驅動（本子題目成果）。本次調整只是把「第一版」從備援提升為本學期主線，第二版移至下學期。

分層與介面都不變：

```
         A（VR 顯示） / B（手部感測）
              ↓  interface-spec.md v1.2（凍結，不因本次調整修改）
      ┌───────┴───────┐
  Python 後端        C 驅動後端
  （本學期主線）      （下學期）
```

### 2.3 一個已排除的可能性

調整前先檢驗過「難」是真的難、還是沒動手過。本人目前的協定層理解明顯高於平均——讀通 STS3215 協定、整理完整 Control Table、並從原廠文件與自己的規格中抓出六處錯誤（F-02、F-15、F-16、F-17、F-22、F-26）。能看出原廠文件寫錯的人不是看不懂底層的人。

真正沒把握的是另一件事：**從零寫出 C 程式碼**。這與 C-13（程式碼由 Claude Code 撰寫、本人 review）有關——看完成品學到的，遠少於自己寫壞再修。

曾評估的最小實驗：手寫收包狀態機（約一百行，規格、測試、模擬器都已就緒）。結論是需要先補 C 的先備知識，因此該實驗與整條 C 路線一併移至下學期（C-26）。先備知識清單列於 4.3，範圍有限，不是無底洞。

## 四、Python 系統的範圍與學習路徑（C-25）

### 4.1 要做什麼

一支 Python 程式，實作 `interface-spec.md` v1.2 的接收端：收 UDP → 驗 CRC → 安全層檢查 → 驅動手臂（LeRobot）→ 選用的狀態回傳。規模約 **150–250 行**，單一檔案。

### 4.2 借與自寫的分界

| 借用 | 自行實作 |
|---|---|
| LeRobot / `feetech-servo-sdk`（伺服機匯流排） | UDP 封包的收送與解析（網路上無任何程式實作本規格） |
| `socket`、`struct`、`time`（標準庫） | 安全層（相對於 LeRobot 的實質貢獻，見 `LeRobot-notes.md` §8） |
| CRC-16/CCITT 實作（`interface-spec.md` §2.3 已附） | 主迴圈與時序控制（綁 100 Hz 目標與 watchdog） |
| 固定頻率迴圈的常見寫法 | 延遲量測與記錄 |

因為封包格式是自訂且已凍結，中間層的黏合程式必然是自己寫的——這是介面凍結的另一個附帶效果。

報告須明確分開「整合的」與「自行實作的」，並標註版本：伺服機通訊採用 LeRobot（commit 待補，V-19），上層 UDP 介面、安全層與延遲量測為自行實作。

### 4.3 先備知識

**Python 側（本學期要學）**

| 項目 | 估時 | 備註 |
|---|---|---|
| `socket` 的 UDP 收送 | 約 1 小時 | 只需 `socket`/`bind`/`recvfrom`/`setblocking` |
| `struct` 的 pack/unpack | 約 1 小時 | 封包格式已熟，剩下是語法 |
| 固定頻率主迴圈 | 約 1 小時 | 以 `perf_counter()` 算下一個喚醒點，不用固定 `sleep` |

**不碰**：asyncio、多執行緒、類別繼承、numpy、任何框架。單一同步迴圈即可，引入這些只會讓除錯變難。

**C 側（下學期補，供日後參考）**

1. 指標與陣列（`uint8_t *buf`、傳陣列給函式）
2. 位元運算（`&`、`|`、`<<`、`>>`、`~`，以及為什麼要 `~x & 0xFF`）
3. `switch` 與 enum（狀態機的骨架）
4. 靜態變數與 struct 存狀態（一次餵一個 byte，狀態要留著）

清單有限。寫完 Python 的 `struct` 之後，第 2 項會變得直覺。

### 4.4 五步路徑

前四步**完全不需要硬體**，與當初做模擬器同一個思路：把「需要真機」壓縮到最後一步。

| 步 | 內容 | 驗證方式 | 需硬體 |
|---:|---|---|---|
| 1 | 綁 49200、收 UDP、印 hex | 用 `interface-spec.md` §7 的發送端當訊號源；應收到 46 bytes | 否 |
| 2 | `struct.unpack` 拆標頭、驗 magic/version/CRC、印六軸角度 | 對照 §2.3 的 NOP 範例封包與 CRC 檢查值 `0x29B1` | 否 |
| 3 | 固定 100 Hz 主迴圈 + 抽乾佇列只留最新一包 | 量測實際週期抖動 | 否 |
| 4 | 安全層 + 假手臂（二十行 dict 存六軸位置） | 送越界角度、壞 CRC、停送 300 ms、送 ESTOP | 否 |
| 5 | 假手臂換成真的 LeRobot bus | 真機 | **是** |

第 2 步有額外價值：那是本人的規格第一次被真正執行。若 CRC 或欄位錯位，問題在規格而非程式，現在發現比 B 寫完橋接才發現便宜得多（對應 V-22）。

第 4 步是相對於 LeRobot 的實質貢獻——它的 `_sync_read` 不檢查 error byte，`max_relative_target` 預設不開（`LeRobot-notes.md` §8）。這塊不底層，是邏輯，報告裡份量足。

## 五、延遲量測不受影響（C-27）

本學期最有份量的智識產出是文獻那塊：Bestmann 的週期模型、FTDI 的 latency timer、以及據此推算的「`0x07` 若維持出廠 500 µs，六顆佔掉 3 ms、頻率掉至 260 Hz」。

**這些量測全部可以用 Python 完成**：

- 單包 READ/WRITE 往返時間
- 六軸 SYNC READ / SYNC WRITE 耗時
- latency timer 預設 vs 調最低的 A/B 對照
- `0x07` 是否可改（V-05）
- 控制迴路延遲 `t1 − t0`（時間戳由 `interface-spec.md` §2.4 規定，兩端同 epoch）

量測區段仍為 `t1 − t0`，C-17 不變：完整端到端 `t2 − t0` 需 L10 與影像鏈，兩者都在下學期。

因此題目中「探討」那一半依然紮實，而且驗證數據反而更快拿到。
