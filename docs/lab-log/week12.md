## 1. 11/24 真機場次：leader 校正後比對與首次 teleoperate

follower 與 leader 都已組裝校正（11/19、11/24 兩場），這是第一次讓 leader 帶 follower 連續遙控。

### 1.1 calibrate 對暫存器做了什麼（F-53 ～ F-56）

**F-53　LeRobot 的 calibrate 會把 Phase 從 92 改成 76。**
C044 / C046 這兩型（leader 的 J1、J3–J6）出廠 Phase 是 92，calibrate 後變 76——差的是 BIT4，也就是多圈模式被清掉改為單圈。C001（follower 與 leader J2）出廠就是 12，BIT4 本來就是 0，calibrate 後維持 12 不變。

這證實了 `LeRobot-notes.md` 4.4 的敘述，也回答了 V-08：出廠值兩種不一致是真的，而 LeRobot 會把它統一掉。

**F-54　leader 的 gripper 被設成扭矩 500。**
其餘五軸沒有這個設定。leader 的 gripper 需要阻力才能給操作者回饋，這是 LeRobot 刻意為之，不是副作用。

**F-55　11/24 的 leader 快照是過渡狀態，不是穩態。**
它取於 calibrate 之後、尚未斷電之前：Lock = 0、`0x29` = 254。follower 的快照則是斷電重開後取的。

**兩份快照不能直接對比**——差異可能來自型號，也可能只是來自「有沒有斷電過」。要比對型號差異，必須在相同的電源狀態下重取。這點要寫進 `snapshots/` 的說明，否則日後拿兩份並排會得出錯的結論。

**F-56　calibrate 之後 `Goal_Position` 仍為 0。**
與 F-49（上電後 `0x2A` 為 0 而非當前位置）一致。這代表 V-29（扭矩打開瞬間韌體會不會把 `0x2A` 同步為當前位置）不是理論問題：如果韌體不同步，開扭矩的瞬間手臂會衝向 0。V-29 的優先序因此提高。

### 1.2 連續遙控 688 秒的時序（F-57 ～ F-59）

LeRobot `teleoperate` 連續跑 688.8 秒，40797 個控制週期，目標 60 Hz，實際 59.23 Hz。

| 迴圈內動作 | 平均 | 最差 | 佔工作時間 |
|---|---|---|---|
| observe（讀 follower 六軸） | 1.23 ms | 6.04 ms | 46.8% |
| teleop（讀 leader 六軸） | 1.14 ms | 73.49 ms | 43.3% |
| send（寫 follower 六軸） | 0.21 ms | 3.49 ms | 7.9% |
| 合計 | 2.6 ms | 76.4 ms | — |

**F-57　匯流排只佔週期預算的 15%。**
一個週期的預算是 16.7 ms，匯流排工作平均 2.6 ms。**這直接否證了文獻推導的瓶頸位置**（詳見 §4 與 `schedule.md` 的「W13 的方向改變」）。

**F-58　剩下的 85% 在等，不是在忙。**
每個週期平均 sleep 14.0 ms（最多 15.9 ms）。40797 個 tick 裡有 20769 個 sleep 睡過頭——將近一半。這是 59.23 Hz 達不到 60 Hz 的原因，問題在迴圈的排程而不在通訊。

**F-59　teleop 最差 73.49 ms，是唯一的異常。**
LeRobot 的摘要寫「超過 16.7 ms 預算的只有 2 個 tick（0.0%）」——**那個「2 次」指的是迴圈內的工作時間，不是整個週期**，所以與 59.23 Hz 不矛盾。這個措辭容易誤讀，引用時要說清楚。

長尾的成因是 W13 的核心問題。

### 1.3 遙控後的快照（F-60 ～ F-63）

**F-60　`0x43–0x44` 在扭矩關閉時是位置的複本。**
停止時 ID 3 的 Goal 是 2988、Present 是 3037，而 `0x43` 讀到 3037——跟 Present 走，不是 Goal。

扭矩**開啟**時尚未驗證。兩者意義完全不同：扭矩關閉時韌體沒在控制任何東西，當位置複本很合理；扭矩開啟時它可能才是韌體一步步逼近的內部目標。V-30 因此只算部分回答。

**F-61　LeRobot 從頭到尾沒有寫過 `Goal_Velocity`。**

這條是三個發現串起來的結論：

- F-17：Phase 的 BIT3 = 1 時，`Goal_Velocity` = 0 代表「全速」而不是「停止」
- F-38：12 顆馬達出廠的 Phase，BIT3 全都是 1
- F-61：LeRobot 從沒寫過這個暫存器，它一直是 0

**所以 LeRobot 的 teleoperate 能動，建立在一個它自己沒有寫下來的假設上。** 如果有一顆馬達的 BIT3 是 0，速度 0 就真的是停止，那顆關節會完全不動，而 LeRobot 不會報錯——它根本沒碰過這個暫存器。整條運動的平滑度實際上只由 Acceleration = 254 一個值在撐。

這是安全層要存在的**實證**而非推測：成熟的開源實作確實依賴了這個預設值。`sim/README.md` 原本寫「驅動端永遠明確寫入速度，不依賴這個行為」是基於原理的保守決定，現在有證據了。

**F-62　LeRobot 斷線後 Lock 留在 0，直到下次斷電。**

```
LeRobot 斷線 → 扭矩關閉、Lock = 0
  ↓
    ← 危險窗口：任何 EEPROM 寫入都永久保存，並消耗 flash 壽命
  ↓
下次斷電上電 → Lock 回到 1
```

依 F-15，Lock = 0 時 EPROM 寫入會進 flash。`snapshot.py` 是唯讀的所以安全，**但 FD 不是**：在這個窗口裡用 FD 改任何 EEPROM 值都會永久生效，而操作者會以為是暫時的。V-13 的急迫性因此提高。

**F-63　熱沒有問題。**
跑約 15 分鐘，溫度從 24–26 °C 升到 32–36 °C，gripper 最高。上限 70 °C，餘裕很大。這條的用途是**排除一個擔憂**而非發現問題：下學期做長時間遙控不必先處理散熱。

## 3. 本週的計畫變更

### C-41　W13 改為定量對照實驗

四個條件（待機／單軸／六軸／負載）各跑 180 秒並逐週期記錄，產出四張圖。完整設計見 `schedule.md` 的「W13 的實驗設計（C-41）」。

兩個設計決定值得在這裡重述，因為它們是方法論而非操作細節：

**四個條件共用同一段程式碼。** `--condition` 只是標籤，不改變任何行為。若四個條件走不同的程式路徑，就分不出差異來自物理條件還是程式分支。因此「待機」的定義是「迴圈照跑、匯流排流量與六軸遙控完全相同，只是人不動 leader」。

**fake 模式是第五個對照組，不只是工具自檢。** 它回答「這台電腦本身有多少抖動」。11/27 在容器上試跑：假裝置的 send 段寫死 0.21 ms，p50 量到 0.211 ms 但 **max 5.661 ms**——沒有匯流排、沒有馬達、沒有 USB，尖峰照樣出現。真機與 fake 的差額才是硬體路徑造成的。

### C-42　C 驅動的硬性規範只約束 `src/`、`sim/`、`tests/`

純 C11、不用 `malloc`、`-Wconversion` 這些規則是在 C 驅動還是主線時寫進 `CLAUDE.md` 的。主線換成 Python（C-25）之後，邊界必須寫明，否則會被誤套到 `pyctrl/`。

**但這留下一個空洞**：寫清楚了什麼不約束 `pyctrl/`，沒寫 `pyctrl/` 歸什麼管。原本是錯誤套用，現在是沒有規範。待補（見 §6）。

### C-43　維持 Windows，但原本的理由已經失效

當初決定不裝 Ubuntu 雙系統的理由是「C 驅動 PC 端本來就要用 Win32」。**C 驅動已經不是主線，這個理由沒了。**

現在的理由是另外三個：

1. 它已經在動了——Windows 上跑出 688 秒連續遙控
2. B 的橋接跑在同一台，localhost UDP，換 OS 要重新協調
3. **W13 正在量的就是 Windows 的排程抖動**，中途換 OS 會讓前後數據不可比

第三點反過來說也成立：**如果 W13 證實長尾是 Windows 排程造成的，「要不要跑 Linux」就從直覺變成有數據支持的下學期議題。** 現在換是逃避問題，量完再換是基於證據。

### C-44　防護規則不得依賴記憶，必須能偵測自己的前提失效

`make layers` 的豁免檔名寫死為 `hal_pc.c`，檔案改名為 `hal_win32.c` 後沒有人回頭看誰引用它；同時 grep 樣式裡漏了 `windows.h`。結果是**檢查照常執行、照常回報「✔ 分層檢查通過」，但實際上什麼都沒擋到**。

**這與 C-30、C-32 不同類。** 前兩次的病因是「東西不在版控可見的地方」，對策是「工具寫好當天進版控」。但 `make layers` 一直在版控裡、每次 `make test` 都跑，照樣失效。照前兩次的教訓做不會防到這一次。

真正的病因是兩層：防護規則裡寫死了會變的東西（檔名），而且**失敗是靜默的**。

對策的第一版是「改名後 grep 舊檔名」。**這一版被否決，因為它自己犯同一個病**——靠紀律的對策，而這條發現正是「靠紀律的防護會靜默失效」。三個月後記得 grep 的機率，跟當初記得更新 `make layers` 的機率一樣。

採用的對策是讓防護**證明自己還在運作**：

1. 豁免清單指向的檔案不存在就直接失敗，改名當場爆掉
2. 通過訊息印出豁免了什麼，「✔ 通過」變成「✔ 通過（豁免：src/hal_win32.c）」，盲目通過變成可察覺

`grep` 舊檔名留作第二道，不當第一道。

**同一個病在本週出現三次**：`make layers` 靜默通過；Project 的 `conversation-split.md` 停在 v1.1 而 repo 已 v1.2；以及本篇 §1.4 的 F 編號——配號當下沒寫進檔案，沒有任何東西會報錯。三者的共通點是「依賴的東西變了，但依賴它的那一方沒跟上，而且不會有人被通知」。

## 4. 工具

**`tools/cadence.py`**（11/27）——固定頻率跑 observe → teleop → send，逐週期記錄計時。

核心限制是**量測不能干擾被量測的東西**，因此迴圈中不寫檔、不配置記憶體、不做單位換算，全部進預配置的 numpy 陣列，跑完才一次寫出。用有緩衝的檔案物件看似無害，但緩衝滿了會自動 flush，製造出等間隔尖峰——那正是要找的 OS 排程特徵，會得到自信但錯誤的結論。

記錄**絕對的 `t_start_ns`** 而不只是各段耗時，否則無法區分「迴圈自己慢」（work 變大）與「迴圈被 OS 搶走」（work 正常但 t_start 間隔變大）。兩者平均週期相同、成因不同。

溫度每 10 秒讀一次會多一筆匯流排交易（fake 實測 work 從 2.6 ms 升到 3.4 ms），該週期以 `temp_read` 標記並在統計時排除，否則每 600 個 tick 污染一個樣本，剛好落在最在意的尾端。

**`tools/cadence_plot.py`**（11/27）——把 CSV 畫成四張圖。

散點圖分上下兩個面板是刻意的：上面板 `work_ns`、下面板 `steal = 週期間隔 − work − sleep`。尖峰的規律程度用算的而不是用看的——找出超過中位數 5 倍的點，量間隔的變異係數，CV < 0.2 指向 OS／USB 的固定排程，CV > 0.8 指向驅動層重試。

**尚未確認**：`cadence.py` 中 LeRobot 的 import 路徑與類別名稱還沒對照 `ba83e4cf` 核過，已在程式中標出。fake 模式不受影響。
